## 상세 기록

### [2026-07-12] 콘솔 한글 깨짐

- 증상: `test_data/_generate_test_data.py` 등 print()로 한글 파일명을 출력하는 스크립트를 Windows 터미널에서 실행하면 한글이 깨져서(mojibake) 출력됨.
- 원인: Python이 파이프/비-conhost 환경에서 stdout 인코딩을 자동 감지할 때 시스템 로케일(cp949)로 폴백하는 경우가 있어, UTF-8로 인코딩된 한글 바이트를 다른 코드페이지로 잘못 해석함.
- 해결 방법: `gui.py`의 `main()`, `barcode_to_cellNum.py`, `cellNum_to_barcode.py`, `test_data/_generate_test_data.py` 시작 부분에 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` (stderr도 동일)를 추가하여 항상 UTF-8로 출력하도록 강제. 서브에이전트가 `PYTHONIOENCODING`/`PYTHONUTF8` 환경변수를 제거한 상태에서도 stdout이 정상 UTF-8로 디코딩됨을 확인.
- 상태: 해결

### [2026-07-12] 파일명 규칙 변경 (GitHub 이슈 #2)

- 증상: [이슈 #2](https://github.com/sfeelBot/46-util/issues/2) 보고 — "파일명의 규칙이 달라졌나봐. 뭔가 잘 안되는 것 같아." 실제 파일명 예시: `0_Test#A8-0000008-1-000-1_Insp_Ver_1_Vertical_Upper_20260711162533_952.raw`
- 원인: 구형 정규식(`\d{4}-\d{2}-\d{2}-(\d+)-`, "YYYY-MM-DD-바코드-" 형식)이 신형 파일명에는 전혀 없음. 대신 `Test#A8-0000008` 같은 "저장번호"가 파일명에 들어있고, 이걸 별도 표로 찾아야 Cell Barcode(`Test_2025_01_16_7632`)를 알 수 있는 구조로 바뀜.
- 해결 방법: `core.py`에 `STORAGE_RE`(`Test#[AB]\d+-\d+`) 정규식과 `load_storage_cellbarcode_map()`을 추가하고, `compute_final_name()`이 구형 패턴을 먼저 시도한 뒤 없으면 신형 패턴(저장번호→Cell Barcode→바코드)을 시도하도록 체인. 이슈 본문의 152행(A/B 저장번호) 표를 파싱해 `mapping/storage_cellbarcode_map.csv`(304행) 생성.
- 상태: 해결

### [2026-07-12] barcode_cell_map.csv 커버리지 부족

- 증상: 이슈 #2의 신형 152개 셀 바코드를 기존 `barcode_cell_map.csv`(110행)와 대조하니 샘플 12개 중 1개만 일치 — 저장번호 매칭 단계를 추가해도 대부분 다음 단계(바코드→셀번호)에서 "매칭실패"로 남을 것으로 예상됨.
- 원인: 기존 110행 매핑표가 최신 전체 셀 목록을 반영하지 못함.
- 해결 방법: 이슈 #2에 달린 댓글(사용자가 두 번 붙여넣은 표, 총 199행+120행)을 파싱해 병합. 병합 규칙: 셀번호별로 실제 바코드 값(`Test_...`)이 있는 쪽을 채택, "바코드 인식 안됨"/"Cell 없음"/빈 값만 있는 셀(12개)은 제외. 병합 결과 두 표 사이에 실제 값 충돌 0건, 기존 110행과의 불일치 0건(순수 추가) 확인 후 `barcode_cell_map.csv`를 110행→247행으로 갱신.
- 주의: `_generate_default_mapping.py`(레거시 하드코딩→CSV 변환용 1회성 스크립트)를 재실행하면 이 확장 내용이 110행짜리 구버전으로 되돌아가므로, 스크립트 상단에 재실행 금지 경고를 추가함.
- 상태: 해결

### [2026-07-12] QTableWidget 시그널 중복 연결 가능성

- 증상(리팩터링 중 발견, 실사용 버그로 보고된 적은 없음): `self.table.itemChanged.connect(self._on_item_changed)`가 `_refresh_table()` 내부에 있어서, 스캔을 여러 번 실행할 때마다 같은 슬롯이 반복 연결됨. 체크박스 하나를 토글하면 스캔 횟수만큼 `_on_item_changed`가 중복 호출될 수 있었음(현재 로직은 멱등적이라 눈에 보이는 오작동은 없었음).
- 원인: `_refresh_table()`이 매 스캔마다 호출되는데 그 안에서 `connect()`를 매번 실행.
- 해결 방법: `connect()` 호출을 `_build_ui()`(최초 1회)로 이동. 서브에이전트가 `table.receivers(itemChanged) == 1`을 스캔 2회 이후에도 확인.
- 상태: 해결

### [2026-07-12] 매칭실패 파일이 결과에서 유실

- 증상: "모두 변환"을 실행하면 매칭실패 파일은 어디로도 복사되지 않고 그냥 목록에서만 확인 가능 — 어떤 파일이 왜 실패했는지 나중에 원본 폴더를 다시 뒤져야 함.
- 해결 방법: `core.convert_files()`/`core.check_conflicts()`에 `copy_errors`(기본 True) 옵션 추가. 매칭실패(`STATUS_NO_MATCH`) 행은 체크 여부와 무관하게 `{출력폴더}/error/`(구조유지 모드면 `error/하위폴더/`)에 원본 파일명 그대로 함께 복사되고, 같은 변환 로그에 포함되어 "되돌리기"로도 함께 원복됨. error 폴더 안에서의 이름 충돌도 정상 변환과 동일하게 사전 충돌검사에 포함됨.
- 상태: 해결

## 검증 요약 (2026-07-13, gui_folder_remap.py 전면 재작성 — 이슈#5 직접 매칭)

서브에이전트 검증 통과, 발견된 버그 없음. `folder_crop_remap.py`(폴더구조 기반, 아래 폐기된 검증 기록 참고)를 대체.

- **load_defect_map**: `storage_ab_defect_info.csv` 304건(152행×A/B) 정상 로드. `Test#A1-0000001`→(`171`,`CU/BALL/400/BC1C2`), `Test#A8-0000032`→(`NULL`,`SUS`), `Test#A7-0000071`→(`NULL`,`AL A`), `Test#A8-0000136`→(`NULL`,`AL B`) 모두 정확.
- **compute_final_name**: A열/B열 양쪽 매칭 모두 정상 동작(예: `Test#B3-0000003` → B열_이물정보 사용). **cell=NULL 행도 매칭실패가 아닌 정상(OK)으로 처리되어 이물정보만으로 변환됨**을 확인(이번 재작성의 핵심 요구사항). 저장번호 패턴 자체가 없는 경우/매핑표에 없는 경우 각각 정확한 사유로 매칭실패. 이물정보의 `/`가 파일명에서 전부 `_`로 치환되어 잘못된 파일명이 생성되지 않음을 확인.
- **전체 파이프라인**: `build_rows`가 5개 행(성공 3 + 실패 2) 반환. `check_conflicts`/`convert_files`/`save_log`/`undo_log`까지 실제 실행해 파일이 정확한 이름·바이트로 복사되고 원본은 그대로 보존됨을 확인. 합성 충돌 케이스(같은 최종명 2개)에서 `ConversionConflictError` 발생 및 파일이 전혀 복사되지 않음도 확인.
- **gui_folder_remap.py 독립성**: `gui.py`/`core.py`/`crop_remap.py`를 전혀 import하지 않고 자체 스캔/변환/되돌리기 로직만으로 `QT_QPA_PLATFORM=offscreen`에서 정상 구동, 위젯 초기화 순서 문제 없음(로그 위젯 생성 후 매핑 로드 로그가 정상 기록됨을 직접 확인).

### (폐기됨) 검증 요약 (2026-07-12, 그룹폴더 기반 Crop 재명명)
